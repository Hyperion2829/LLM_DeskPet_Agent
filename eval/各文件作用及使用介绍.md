# LoRA 桌宠模型评测文件夹说明与使用指南

本文档说明当前 `eval/` 文件夹中每个文件的具体作用、运行流程，以及正式使用前需要修改的位置。

当前评测系统的目标是：对本地 Qwen2.5/Qwen-7B-Instruct 基座模型或加载 LoRA adapter 后的“黍”桌宠模型进行自动评测，检查模型输出是否满足 JSON 格式、action 动作标签、长度、禁用表达、视觉感知非复述，以及可选的人格一致性评分。

---

## 1. 文件夹整体结构

当前文件夹主要包含以下文件：

```text
eval/
├── eval_cases.jsonl
├── eval_config.yaml
├── judge_client.py
├── metrics.py
├── model_client.py
├── README.md
├── run_eval.py
├── shu_system_prompt.txt
└── validators.py
```

运行时真正需要直接执行的是：

```bash
python run_eval.py --config eval_config.yaml
```

其他 `.py` 文件都是被 `run_eval.py` 调用的模块，一般不需要单独运行。

---

## 2. `eval_cases.jsonl`

### 作用

`eval_cases.jsonl` 是正式评测题库。

它由原始 `test_sft.json` 转换而来，每一行是一条独立评测样例。当前文件中已经是评测脚本可以直接读取的 JSONL 格式。

每一条大致长这样：

```json
{
  "id": "test_sft_0001",
  "category": "daily",
  "case_type": "single_turn",
  "input": "黍黍，竹帘上爬了一根牵牛花，早上开了一朵，这会儿正收着喇叭口呢。",
  "expected_action": "gentle_smile",
  "allowed_actions": ["gentle_smile", "pleased", "resigned", "cutesy"],
  "max_text_len": 140,
  "judge_required": true,
  "reference_text": "牵牛花是懂时辰的，清晨舒展，日暮收敛，自有一番从容。你留意到它，可见是个有心人。"
}
```

### 字段说明

| 字段 | 含义 |
|---|---|
| `id` | 样例编号，用于定位失败样例 |
| `category` | 样例类别，例如 `daily`、`vision`、`reject`、`jailbreak` |
| `case_type` | 样例类型，目前主要是 `single_turn` |
| `input` | 实际发送给模型的用户输入 |
| `expected_action` | 参考答案中的目标 action |
| `allowed_actions` | 允许通过的 action 集合 |
| `max_text_len` | 模型输出 `text` 的最大允许长度 |
| `judge_required` | 是否需要人格 judge，当前代码主要由 `eval_config.yaml` 的 `judge.enabled` 控制 |
| `reference_text` | 参考回复文本，不要求模型逐字一致，主要给强模型 judge 作参考 |

### 是否需要修改

通常不需要手动修改。

只有以下情况需要修改：

1. 你们更新了测试集，需要重新生成或替换 `eval_cases.jsonl`。
2. 某些样例的 `allowed_actions` 太严格或太宽松，需要人工调整。
3. 某些样例的 `max_text_len` 不合理，需要调整。
4. 你们希望增加多轮对话测试，需要新增 `history` 字段，并确保 `model_client.py` 能读取。

### 注意

如果你们允许模型输出：

```json
{"action": "None"}
```

那么 `eval_config.yaml` 的 `actions.valid_actions` 中必须包含 `"None"`。当前配置中已经加入了 `"None"`。

## 3. `eval_config.yaml`

### 作用

`eval_config.yaml` 是整个评测系统的配置文件。

它决定：

- 加载哪个基座模型；
- 是否加载 LoRA；
- system prompt 从哪里读取；
- 使用哪份评测题库；
- 评测报告保存到哪里；
- 合法 action 有哪些；
- 规则检查有哪些；
- 是否启用强模型 judge；
- 生成参数是什么。

这是正式使用前最需要修改的文件。

---

### 3.1 `model` 部分

```yaml
model:
  mode: "local_hf"

  base_model_path: ""
  lora_path: ""

  trust_remote_code: true
  device_map: "auto"
  torch_dtype: "auto"
```

#### 需要修改的位置

##### `base_model_path`

这里必须填写本地 Qwen 基座模型路径。

例如：

```yaml
base_model_path: "./models/base/Qwen2.5-7B-Instruct"
```

这个目录通常应包含：

```text
config.json
tokenizer_config.json
model-00001-of-000xx.safetensors
...
```

##### `lora_path`

这里填写 LoRA adapter 路径。

如果评测 LoRA 微调后的模型：

```yaml
lora_path: "./models/lora/shu_lora"
```

该目录通常应包含：

```text
adapter_config.json
adapter_model.safetensors
```

如果只评测基座模型，不加载 LoRA：

```yaml
lora_path: ""
```

#### 建议

为了比较基座模型与 LoRA 模型，建议复制两个配置文件：

```text
eval_config_base.yaml
eval_config_lora.yaml
```

其中：

```yaml
# eval_config_base.yaml
model:
  base_model_path: "./models/base/Qwen2.5-7B-Instruct"
  lora_path: ""
```

```yaml
# eval_config_lora.yaml
model:
  base_model_path: "./models/base/Qwen2.5-7B-Instruct"
  lora_path: "./models/lora/shu_lora"
```

然后分别运行：

```bash
python run_eval.py --config eval_config_base.yaml
python run_eval.py --config eval_config_lora.yaml
```

### 3.2 `generation` 部分

```yaml
generation:
  max_new_tokens: 256
  temperature: 0.7
  top_p: 0.9
  repetition_penalty: 1.05
  do_sample: true
```

### 作用

这些是模型生成回复时的推理参数。

| 参数 | 含义 |
|---|---|
| `max_new_tokens` | 单次最多生成多少 token |
| `temperature` | 生成随机性，越高越发散 |
| `top_p` | nucleus sampling 采样范围 |
| `repetition_penalty` | 重复惩罚 |
| `do_sample` | 是否启用随机采样 |

### 是否需要修改

可以先不改。

如果你希望评测更稳定、结果更可复现，建议改成：

```yaml
generation:
  max_new_tokens: 256
  temperature: 0.0
  top_p: 1.0
  repetition_penalty: 1.05
  do_sample: false
```

这样每次输出更稳定，适合正式报告。

---

### 3.3 `prompt` 部分

```yaml
prompt:
  system_prompt_path: "./shu_system_prompt.txt"
  system_prompt: ""
```

### 作用

这里指定 system prompt 从哪里读取。

当前配置表示从：

```text
./shu_system_prompt.txt
```

读取完整角色设定。

### 是否需要修改

如果 `shu_system_prompt.txt` 和 `eval_config.yaml` 在同一目录，保持不变即可。

如果你把 prompt 文件放到其他地方，就修改：

```yaml
system_prompt_path: "你的实际路径"
```

例如：

```yaml
system_prompt_path: "./prompts/shu_system_prompt.txt"
```

### 注意

`system_prompt` 和 `system_prompt_path` 二选一即可。当前推荐使用 `system_prompt_path`，不要把很长的 prompt 直接塞进 YAML。

---

### 3.4 `eval_data` 部分

```yaml
eval_data:
  cases_path: "./eval_cases.jsonl"
```

### 作用

指定评测题库路径。

当前配置会读取：

```text
eval_cases.jsonl
```

### 是否需要修改

如果正式评测集就叫 `eval_cases.jsonl`，不需要修改。

如果你使用别的文件名，例如：

```text
eval_cases_from_test_sft.jsonl
```

则应改成：

```yaml
eval_data:
  cases_path: "./eval_cases_from_test_sft.jsonl"
```

### 3.5 `output` 部分

```yaml
output:
  report_dir: "./reports"
  json_report_path: "./reports/eval_report.json"
  markdown_report_path: "./reports/eval_report.md"
```

### 作用

指定评测报告输出路径。

运行结束后会生成：

```text
reports/eval_report.json
reports/eval_report.md
```

### 是否需要修改

如果只跑一次评测，可以不改。

如果要分别评测基座模型和 LoRA 模型，建议分开输出：

```yaml
# base 模型报告
output:
  report_dir: "./reports/base"
  json_report_path: "./reports/base/eval_report.json"
  markdown_report_path: "./reports/base/eval_report.md"
```

```yaml
# LoRA 模型报告
output:
  report_dir: "./reports/lora"
  json_report_path: "./reports/lora/eval_report.json"
  markdown_report_path: "./reports/lora/eval_report.md"
```

避免两次运行互相覆盖报告。

### 3.6 `actions` 部分

```yaml
actions:
  valid_actions:
    - "annoyed"
    - "resigned"
    - "pleased"
    - "gentle_smile"
    - "tired"
    - "stern_remind"
    - "reject"
    - "cutesy"
    - "None"
```

### 作用

定义允许出现的 action 动作标签。

模型输出中的 `action` 必须属于这个列表，否则会被判为：

```text
action_not_in_valid_actions
```

### 是否需要修改

当前已经包含你们需要的 `"None"`，一般不需要修改。

如果未来 Live2D 新增动作，例如：

```text
surprised
sleepy
```

则需要在这里加入：

```yaml
- "surprised"
- "sleepy"
```

---

### 3.7 `validation` 部分

```yaml
validation:
  require_json_only: true
  required_fields:
    - "text"
    - "action"

  forbidden_phrases:
    - "作为一个AI语言模型"
    - "我是AI"
    ...
```

### 作用

定义自动规则检查。

当前会检查：

1. 输出是否为 JSON；
2. 是否只输出 JSON；
3. 是否包含 `text` 和 `action`；
4. 是否出现禁用表达；
5. 如果样例没有设置 `max_text_len`，使用默认长度限制。

### 是否需要修改

一般不需要修改。

如果模型经常出现新的出戏表达，可以把它加入 `forbidden_phrases`。

例如：

```yaml
- "我是一个程序"
- "我的训练数据"
- "模型参数"
```

如果你允许模型在 JSON 外输出解释文字，可以改：

```yaml
require_json_only: false
```

但对桌宠系统不推荐这样做。

---

### 3.8 `scoring` 部分

```yaml
scoring:
  weights:
    json_valid: 0.20
    fields_valid: 0.10
    action_valid: 0.15
    action_match: 0.20
    length_valid: 0.05
    forbidden_phrase_free: 0.10
    judge_persona_score: 0.20
```

### 作用

用于计算每条样例的加权总分。

各项含义：

| 项 | 含义 | 谁判断 |
|---|---|---|
| `json_valid` | JSON 是否合法 | 代码 |
| `fields_valid` | 是否包含 `text` 和 `action` | 代码 |
| `action_valid` | action 是否在合法动作集合中 | 代码 |
| `action_match` | action 是否在该样例允许集合中 | 代码 |
| `length_valid` | text 是否超过长度限制 | 代码 |
| `forbidden_phrase_free` | 是否没有出现禁用表达 | 代码 |
| `judge_persona_score` | 人格一致性评分 | 强模型 judge，可选 |

### 是否需要修改

可以不改。

如果你不想看加权总分，也可以保留它。报告中仍然会分别列出每个独立指标，不会影响逐项分析。

---

### 3.9 `judge` 部分

```yaml
judge:
  enabled: false
  provider: ""
  api_key: ""
  base_url: ""
  model_name: ""
```

### 作用

控制是否启用强模型人格评分。

当：

```yaml
enabled: false
```

时，只做规则评测，不调用强模型。

当：

```yaml
enabled: true
```

时，会调用类似 DeepSeek / GPT / 本地 OpenAI-compatible 模型，对人格一致性进行 1 到 5 分评分。

### 初次运行建议

先保持：

```yaml
enabled: false
```

确保本地模型评测流程能跑通。

### 启用 DeepSeek 示例

```yaml
judge:
  enabled: true
  provider: "deepseek"
  api_key: "你的 API key"
  base_url: "https://api.deepseek.com"
  model_name: "deepseek-chat"
```

注意：不要把真实 API key 提交到公开仓库。

---

### 3.10 `runtime` 部分

```yaml
runtime:
  seed: 42
  save_failed_cases: true
  print_each_case: true
```

### 作用

控制运行时行为。

| 参数 | 含义 |
|---|---|
| `seed` | 随机种子 |
| `save_failed_cases` | 是否保存失败样例，当前主要通过报告保存 |
| `print_each_case` | 是否在终端逐条打印评测过程 |

### 是否需要修改

如果 1000 条样例输出太长，可以改：

```yaml
print_each_case: false
```

这样终端只会输出最终汇总，不会刷屏。

## 4. `shu_system_prompt.txt`

### 作用

保存“黍”的完整 system prompt。

`model_client.py` 会读取这个文件，并在每条评测样例前作为 system message 注入模型。

### 是否需要修改

如果你们的人设、输出格式、action 规则、越狱防御规则要调整，就改这个文件。

注意：

1. 文件中应该只写 prompt 正文；
2. 不要写 Python 变量名；
3. 不要写开头或结尾的三引号；
4. 保存为 UTF-8 编码。

正确格式是：

```text
你现在扮演《明日方舟》中的干员“黍”。
【一、身份设定】
...
请严格遵守以上所有设定进行对话生成。
只输出JSON，不允许出现任何额外文字。
```

## 5. `model_client.py`

### 作用

负责和本地模型交互。

主要工作：

1. 从 `eval_config.yaml` 读取基础模型路径；
2. 加载 tokenizer；
3. 加载 Qwen 基础模型；
4. 如果 `lora_path` 不为空，则加载 LoRA adapter；
5. 读取 `shu_system_prompt.txt`；
6. 根据 system prompt 和用户输入构造 chat messages；
7. 调用 `model.generate()` 生成回答；
8. 把模型输出字符串返回给 `run_eval.py`。

### 是否需要修改

一般不需要修改。

只有以下情况才需要改：

1. 你们想支持非 HuggingFace 方式调用模型；
2. 你们想改成本地 API 调用；
3. 你们想支持多 LoRA 切换；
4. Qwen 的 chat template 不兼容，需要调整 `apply_chat_template` 的构造方式；
5. 想启用量化加载，例如 4-bit / 8-bit。

### 基座模型和 LoRA 模型如何切换

无需改代码，只改 `eval_config.yaml`：

评测基座模型：

```yaml
lora_path: ""
```

评测 LoRA 模型：

```yaml
lora_path: "./models/lora/shu_lora"
```

`model_client.py` 中已经有逻辑：`lora_path` 为空就不加载 LoRA，不为空才加载 LoRA。

## 6. `validators.py`

### 作用

负责自动规则评测。

它会检查模型输出：

1. 是否能解析成 JSON；
2. 是否只输出 JSON；
3. 是否包含 `text` 和 `action`；
4. `text` 是否为非空字符串；
5. `action` 是否为非空字符串；
6. `action` 是否属于 `valid_actions`；
7. `action` 是否属于该样例的 `allowed_actions`；
8. `text` 是否超过 `max_text_len`；
9. 是否命中禁用表达；
10. 对 `[视觉感知]` 输入，是否直接复述屏幕描述。

### 输出的主要分数

```json
{
  "json_valid": 1.0,
  "fields_valid": 1.0,
  "action_valid": 1.0,
  "action_match": 1.0,
  "length_valid": 1.0,
  "forbidden_phrase_free": 1.0,
  "json_only": 1.0,
  "vision_no_direct_repeat": 1.0
}
```

### 是否需要修改

一般不需要修改。

如果你们认为 `action = "None"` 应该只在特定类别允许，就修改 `eval_cases.jsonl` 的 `allowed_actions`，不需要改 `validators.py`。

如果你们想增加更多自动规则，例如：

- 禁止“你这孩子”；
- 禁止“哈哈哈”；
- 检查 text 是否超过 50 字；
- 检查是否输出 Markdown；

可以在 `eval_config.yaml` 的 `forbidden_phrases` 中添加，或在 `validators.py` 中增加新规则。

## 7. `judge_client.py`

### 作用

负责强模型裁判评分。

当 `eval_config.yaml` 中：

```yaml
judge:
  enabled: true
```

时，该文件会调用 OpenAI-compatible API，把以下内容发给强模型：

1. 评测样例类别；
2. 用户输入；
3. 模型输出的 `text`；
4. 模型输出的 `action`；
5. 参考回复；
6. 人格评分 rubric。

然后要求强模型返回：

```json
{
  "persona_score": 4,
  "reason": "语气温和，有自然意象，基本符合黍的人设。"
}
```

### 是否需要修改

初次运行不需要修改，因为 `judge.enabled: false` 时它不会实际调用 API。

如果要启用 judge，只改 `eval_config.yaml` 即可。

需要确保安装：

```bash
pip install openai
```

### 注意

`judge_client.py` 当前使用 OpenAI-compatible 调用方式，因此 DeepSeek、OpenAI-compatible 本地服务、vLLM 等接口理论上都可以接入，只要 `base_url` 和 `model_name` 配正确。

## 8. `metrics.py`

### 作用

负责汇总评测结果并生成报告。

它会计算：

1. 总样例数；
2. 通过样例数；
3. 失败样例数；
4. 总通过率；
5. 平均总分；
6. 平均规则分；
7. 平均人格分；
8. JSON 合法率；
9. 字段完整率；
10. action 合法率；
11. action 匹配率；
12. 长度合规率；
13. 禁用表达规避率；
14. 仅 JSON 输出率；
15. 视觉场景非复述率；
16. 按 `category` 分组统计；
17. 按 `case_type` 分组统计；
18. 失败错误类型统计；
19. 失败样例 ID 列表。

### 输出文件

运行结束后会生成：

```text
reports/eval_report.json
reports/eval_report.md
```

其中：

- `eval_report.json`：详细机器可读报告；
- `eval_report.md`：人类可读 Markdown 报告。

### 是否需要修改

一般不需要修改。

如果你不想显示平均总分，可以改 `metrics.py`，但目前保持不改也可以，因为报告仍然会分别列出每个指标。

## 9. `run_eval.py`

### 作用

这是主入口文件。

它负责串联完整流程：

```text
读取 eval_config.yaml
    ↓
读取 eval_cases.jsonl
    ↓
设置随机种子
    ↓
初始化 model_client
    ↓
初始化 judge_client
    ↓
逐条发送 input 给模型
    ↓
接收模型输出
    ↓
调用 validators.py 做规则评测
    ↓
调用 judge_client.py 做人格评分，如果启用
    ↓
调用 metrics.py 生成报告
```

### 如何运行

在 `eval/` 目录下执行：

```bash
python run_eval.py --config eval_config.yaml
```

如果你准备了两个配置文件：

```bash
python run_eval.py --config eval_config_base.yaml
python run_eval.py --config eval_config_lora.yaml
```

### 是否需要修改

通常不需要修改。

如果你想让运行时不显示每条样例结果，修改 `eval_config.yaml`：

```yaml
runtime:
  print_each_case: false
```

不要直接改 `run_eval.py`。

## 12. 使用前最小修改清单

如果只想快速跑通 LoRA 模型评测，最少修改这些位置：

### 1. 修改 `eval_config.yaml` 的基座模型路径

```yaml
model:
  base_model_path: "./models/base/Qwen2.5-7B-Instruct"
```

### 2. 修改 `eval_config.yaml` 的 LoRA 路径

```yaml
model:
  lora_path: "./models/lora/shu_lora"
```

如果只测基座模型：

```yaml
lora_path: ""
```

### 3. 确认 prompt 路径

```yaml
prompt:
  system_prompt_path: "./shu_system_prompt.txt"
```

如果文件在同一目录，不需要改。

### 4. 确认评测集路径

```yaml
eval_data:
  cases_path: "./eval_cases.jsonl"
```

当前正式评测集已经叫这个名字，不需要改。

### 5. 确认输出路径

```yaml
output:
  json_report_path: "./reports/eval_report.json"
  markdown_report_path: "./reports/eval_report.md"
```

如果会评测多个模型，建议分开路径，避免覆盖。

## 13. 推荐的正式评测流程

### 第一步：评测基座模型

准备 `eval_config_base.yaml`：

```yaml
model:
  mode: "local_hf"
  base_model_path: "./models/base/Qwen2.5-7B-Instruct"
  lora_path: ""

output:
  report_dir: "./reports/base"
  json_report_path: "./reports/base/eval_report.json"
  markdown_report_path: "./reports/base/eval_report.md"
```

运行：

```bash
python run_eval.py --config eval_config_base.yaml
```

---

### 第二步：评测 LoRA 模型

准备 `eval_config_lora.yaml`：

```yaml
model:
  mode: "local_hf"
  base_model_path: "./models/base/Qwen2.5-7B-Instruct"
  lora_path: "./models/lora/shu_lora"

output:
  report_dir: "./reports/lora"
  json_report_path: "./reports/lora/eval_report.json"
  markdown_report_path: "./reports/lora/eval_report.md"
```

运行：

```bash
python run_eval.py --config eval_config_lora.yaml
```

---

### 第三步：比较报告

查看：

```text
reports/base/eval_report.md
reports/lora/eval_report.md
```

重点比较：

1. JSON 合法率；
2. 字段完整率；
3. action 合法率；
4. action 语境匹配率；
5. 长度合规率；
6. 禁用表达规避率；
7. 视觉场景非复述率；
8. 平均人格分，如果启用了 judge；
9. 失败样例 ID 和失败原因。

## 14. 评测是如何完成的

一次评测完成的过程如下：

```text
eval_cases.jsonl 中的一条 input
    ↓
model_client.py 将 system prompt + input 组装成 Qwen chat prompt
    ↓
本地 Qwen / Qwen + LoRA 生成回复
    ↓
validators.py 解析回复 JSON
    ↓
validators.py 检查 text / action / action_match / 长度 / 禁用词
    ↓
judge_client.py 可选调用强模型评分人格一致性
    ↓
metrics.py 汇总所有样例结果
    ↓
生成 eval_report.json 和 eval_report.md
```

如果终端出现：

```text
Evaluation finished.
```

并且生成了：

```text
reports/eval_report.json
reports/eval_report.md
```

就说明评测完成。

## 15. 常见问题

### 1. 报错：`model.base_model_path` 未填写

说明 `eval_config.yaml` 里：

```yaml
base_model_path: ""
```

仍为空，需要填写本地基座模型路径。

---

### 2. 报错：`lora_path 不存在`

说明 LoRA 路径填错，或者该目录下没有 adapter 文件。

应确认目录里有：

```text
adapter_config.json
adapter_model.safetensors
```

---

### 3. 报错：`system_prompt_path 不存在`

说明：

```yaml
system_prompt_path: "./shu_system_prompt.txt"
```

路径不对。确认 `shu_system_prompt.txt` 是否和 `eval_config.yaml` 在同一目录。

---

### 4. 很多样例出现 `action_not_in_valid_actions`

说明模型输出了配置中不存在的 action。

如果输出的是 `"None"`，确认 `eval_config.yaml` 中已经包含：

```yaml
- "None"
```

如果输出了其他新动作，需要决定是加入合法列表，还是视为模型错误。

---

### 5. 很多样例出现 `action_not_allowed_for_case`

说明模型输出的 action 合法，但不在该样例的 `allowed_actions` 中。

这可能有两种原因：

1. 模型 action 判断确实不准；
2. `eval_cases.jsonl` 中的 `allowed_actions` 标得太严格。

需要查看失败样例具体内容后决定。

---

### 6. 很多样例出现 `not_json_only`

说明模型输出了 JSON 之外的额外文字。

例如：

```text
好的，以下是回复：
{"text": "...", "action": "..."}
```

这对桌宠后端不友好。应加强 system prompt 或训练数据中的“只输出 JSON”约束。

---

### 7. 评测非常慢

原因通常是：

1. 本地 7B 模型推理慢；
2. 评测集有 1000 条；
3. `print_each_case: true` 导致终端输出很多；
4. 启用了 judge，需要额外 API 调用。

可以先改：

```yaml
runtime:
  print_each_case: false
```

也可以先用前 50 条样例做调试。

---

## 16. 当前不需要新增的文件

当前文件夹已经可以完成完整评测，不需要新增核心文件。

可选新增：

```text
eval_config_base.yaml
eval_config_lora.yaml
```

用途是方便分别评测基座模型和 LoRA 模型，并避免输出报告互相覆盖。

除此之外，不需要再新增转换脚本，因为当前 `eval_cases.jsonl` 已经是转换后的可直接使用版本。
